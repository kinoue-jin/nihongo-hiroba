## 過剰実装の抑制（全言語共通）

🔴 **コードを書く前に下の「はしご」を上から降り、最初に成り立つ段で止める。**

```
1. これは存在する必要があるか？               → no なら作らない（YAGNI）
2. 既にこのコードベースにあるか？             → 再利用する（書き直さない）
3. 標準ライブラリでできるか？                 → 使う
4. プラットフォームのネイティブ機能でできるか？ → 使う（例: 日付入力は `<input type="date">`）
5. 導入済みの依存でできるか？                 → 使う
6. 1 行で済むか？                             → 1 行で
7. ここで初めて「動く最小限」を書く
```

- ⚠ **怠惰なのは解法についてだけで、読むことには怠惰でない。** はしごは問題理解の代替ではなく、
  **変更が触れるコードを読み実フローを追った後**の刈り込みである。読まずに 1 を選ぶのは手抜き。
- 🔴 **削ってはいけないもの**: 信頼境界の検証 / データ喪失の処理 / セキュリティ / アクセシビリティ。
  コードが小さくなるのは「必要だから」であって短縮競争ではない（**怠惰 ≠ 手抜き**）。
  ⚠ 原典のベンチでも、素朴な「YAGNI + 一行主義」プロンプトだけが安全性を落としている（100% → 95%）。
- **射程（なぜ本節が要るか）**: handoff の scope creep 検知（票の対象ファイル）は **Target 一覧というファイル範囲**を
  守るルールで、**同一ファイル内の書きすぎ**（仕様にない「将来のための」設定項目・抽象レイヤ・
  ラッパー）は捕まえられない。本節はその空白を埋める。
- **出典と限界**: `DietrichGebert/ponytail` の 7 段はしごから**判断手順だけを移植**した
  （整理は `LLM-Wiki/wikis/tech/wiki/ponytail-lazy-senior-dev.md`）。
  🔴 **原典の実測値（LOC −54% 等）を根拠に使わないこと。** ベンチは **Haiku 4.5・n=4** で、
  **当環境（実装・review の model は `norms:tiers.reviewer_model`）での再現は未検証**。原典自身が
  「段を熟慮する高推論モデルではトークンが逆に増えうる」と注記しており、その検証は未了である。
  採るのは手順であって効果の数値ではない。

## TypeScript (Frontend)
- TypeScript strict mode
- 関数コンポーネント + hooks
- named export 推奨
- パスエイリアス: `@/` = `src/`
- 🔴 **`setTimeout` / `setInterval` の危険度は「遅延の長さ」でも「解除の有無」でもなく、
  callback が React の dispatch を握っているかで決まる**（2026-08-11 [PROMOTED]）。
  - **危険 = callback が `setXxx`（`useState` の dispatch）を閉じ込めている形。** unmount 後も
    `dispatchSetState` → `requestUpdateLane` → `getCurrentEventPriority` と進み、**teardown 後は
    `window` 参照で落ちる**（react-dom 18.3.1 実測: root の null 判定より**前**に `requestUpdateLane` が
    無条件で呼ばれる）。症状は full suite の間欠 `Errors 1` / exit 1。
  - **安全 = callback が外部ストアの `notify()` だけを叩く形。** 購読者は `useSyncExternalStore` の
    unsubscribe で unmount 時に消えるため、teardown 後は空 Set を回すだけになる。ref 更新のみも同様。
  - **母数の取り方**: `setTimeout` × `set[A-Z]` 軸で grep し、`clearTimeout` を持つファイルを除く。
    ⚠ **エラーメッセージ（`window is not defined`）を軸に grep しても、「解除処理の不在」という
    コードの不在は母数に現れない。** ⚠ 同一行 grep では**複数行にまたがる形**を取りこぼすので、
    ファイル単位で当たりを付けてから中身を読む。
  - 🔴 **この bug class はテストでは守れない**（判定軸とセットで読むこと）。生きた jsdom では
    `window` があるので setState は成功して no-op になり、React 18 は unmount 済み fiber への setState を
    警告しない。**exit code にも `Errors` 行にも痕跡が残らないため摂動テストでも検出できない**
    （実測: 該当ガードを外す摂動が 7 本中 **0 本**しか落とさなかった。対照 = full suite の exit code が
    異常を示す一般的な検知経路 → rules/testing-pitfalls.md#full-suite-exit-code-errors）。
    **規約と grep でしか守れない。**
    ⚠ 判定軸だけを読むと「テストを足せば守れる」と誤読される。

## Shell (スクリプト / テスト harness)

- 🔴 **非 ASCII 文字に隣接する変数展開は必ず `${var}` と波括弧を付ける**（2026-08-06 [PROMOTED]）。
  bash の変数名終端判定はロケール依存で、UTF-8 では**多バイト文字の先頭バイトを名前構成文字とみなし得る**。
  実測: `detail="... actual=$rc（...）"` で **`$rc` の値が消え、全角括弧 `（`（`EF BC 88`）の先頭バイトまで
  変数名として食われ、残り `BC 88` が生バイトで出力された**。
  - ⚠ **ASCII の区切り（空白 / `;` / `"`）が続く限り顕在化しない**ため、日本語メッセージの中で
    変数展開を書いたときにだけ出る。
  - ⚠ **影響が assert ではなく診断文言に出る**ので、テストは PASS のまま**壊れた出力だけが残る**
    ＝ FAIL 時にしか見えず、その FAIL 時にこそ読めなくなる。実際に不正 UTF-8 が
    `subprocess(text=True)` の `UnicodeDecodeError` を誘発し、**摂動の復元漏れ事故**につながった。
  - **検出**（2026-08-09 [PROMOTED] で差し替え）: **非 ASCII を「バイト」で判定する形だけを使う。**
    ```
    LC_ALL=C grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]' <script>
    python3 -c "import re,sys;p=re.compile(r'\\\$[A-Za-z_][A-Za-z0-9_]*[^\x00-\x7f]');[print(f'{n}:{l}',end='') for n,l in enumerate(open(sys.argv[1]),1) if p.search(l)]" <script>
    ```
    🔴 **以前の検出コマンド `grep -nE '\$[a-z_]*[（）「」]'` は使わない** — 違反が 6 箇所実在する状態で **0 件**を返した（実測）。
    - 🔴 **真因は変数名側の文字クラス `[a-z_]*` が数字・大文字を含まないこと**。実データの違反は `$rc29（…` の形で、
      `[a-z_]*` が `rc` まで食った直後に `2` が来るため照合が外れる。
    - ⚠ **「多バイト文字をブラケット式に入れると BSD grep が照合しない」という当初の診断は誤り**（2026-08-09 に再検証）。🔴 **ただし `LC_ALL=C`（または `LANG` 未設定）の下では成立する**（2026-09-11 [PROMOTED]）: bracket がバイトの集合になり 3 バイトの `—` `–` は 1 バイトずつに分かれて恒偽。検査 script の `LC_ALL=C grep` では多バイトの選択肢を alternation `(—|–)` で書く。Bash ツールのシェルの `grep` は harness 関数（ugrep）でロケールに依らず一致するため手元では再現しない — 再現は `bash file.sh` 経由で。
      実測（BSD grep 2.6.0-FreeBSD / ugrep 7.5.0 の**両方で同一**・`LANG=ja_JP.UTF-8`）:
      `$rc（` は旧パターンで**拾える** / `$rc29（` は**拾えない** / `[a-z0-9_]` へ広げると**拾える**。
    - **それでも差し替える理由は 2 つ**: ①列挙した 4 文字しか見ない（他の全角記号は素通り）②変数名の文字クラスを
      手で正しく書き切る必要がある。**バイト判定なら両方が構造的に閉じる**（大文字・数字・全ての非 ASCII を含む）。
    ⚠ **0 件の出力は安心の根拠として機能してしまう**（実行できているのに検出力がゼロ）。捕まえたのは検出コマンドではなく FAIL 出力を人が読んだことだった。
  - 🔴 **規約が検出コマンドを規定するときは、そのコマンド自体を「違反を 1 件仕込んで拾えるか」で検証してから載せる**（＝ 検出手段にも RED を要求する）。上記の旧コマンドは**一度も検証されないまま [PROMOTED] され、さらに「なぜ効かないか」の診断も未検証のまま起票された**（2 段で検証が抜けた）。
  - ⚠ **[PROMOTED] 済みの規約でも、サブエージェントには届かない**。本違反は独立テスト作者（サブ）が新規に書いたコードで再発した。実装 / テスト作者サブの prompt に「bash 3.2 互換」と並べて本節を明記するか、**統合者が commit 前に上記の検出を回すことを手順化する**。
- 🔴 **複数ファイルを 1 回の `awk` に渡すとき、出典の帰属は `FILENAME` ではなく「レコード開始時に控えた変数」で決める**（2026-08-06 [PROMOTED]）。
  awk は**次ファイルの第 1 レコードを処理する前に `FILENAME` を更新する**ため、ファイル末尾で
  「まだ確定していないレコード」を抱えたまま次ファイルへ進むと、**flush した時点の `FILENAME` は既に次ファイル**になる。
  - ⚠ **`FNR==1` でファイル境界をリセットするだけでは直らない**（実測）。`FNR==1 { flush() }` の flush も
    新しい `FILENAME` で出力する。**ガードあり = ガードなし = 誤った帰属**という結果になり、
    「ガードを足したから直った」という誤った安心を生む。
  - **対処**: レコード開始時に `fn = FILENAME` を控え、出力は `fn` を使う。境界リセット（`FNR==1`）は
    **状態の持ち越しを切るため**に併用する（帰属と状態は別の問題なので**両方**必要）。
  - ⚠ **発生条件は例外的ではない**。実測では `_archive/` + `request.md` の **61 ファイル**が
    「レコード未確定のまま EOF」に該当した。集計の総数は合っていても**内訳の帰属だけが静かにずれる**ので、
    総数の突合では検出できない。
- macOS 標準は **bash 3.2**。`mapfile` / `readarray` / 連想配列（`declare -A`）/ `${var,,}` 等の
  bash 4+ 専用機能は使わない（PO の実機が macOS のため）。
